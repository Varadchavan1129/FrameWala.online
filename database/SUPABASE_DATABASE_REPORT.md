# Supabase Database Migration Report

This report documents the conversion of the FrameWala MySQL database to a PostgreSQL (Supabase) compatible schema. 

## 1. Complete Table List & Execution Order
To maintain referential integrity, the tables must be created and destroyed in a specific dependency order. 

**Creation Order:**
1. `users`
2. `categories`
3. `products` (depends on `categories`)
4. `product_images` (depends on `products`)
5. `addresses` (depends on `users`)
6. `cart` (depends on `users`)
7. `cart_items` (depends on `cart`, `products`)
8. `wishlist` (depends on `users`, `products`)
9. `orders` (depends on `users`, `addresses`)
10. `order_items` (depends on `orders`, `products`)
11. `payments` (depends on `orders`)
12. `shipments` (depends on `orders`)
13. `reviews` (depends on `users`, `products`)

*Note: Deletion (DROP) order is the exact reverse of the creation order to prevent foreign-key violations, which is automatically handled in PostgreSQL via `CASCADE`.*

## 3. MySQL-to-PostgreSQL Conversions Made

1. **AUTO_INCREMENT & Keys:** All `AUTO_INCREMENT PRIMARY KEY` declarations were converted to PostgreSQL native `INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`.
2. **Timestamps:** Converted all `TIMESTAMP` and `DATETIME` columns to `TIMESTAMPTZ` (Timezone-aware timestamps) to ensure global compatibility.
3. **Database Selection:** Removed `CREATE DATABASE IF NOT EXISTS` and `USE framewala_db` syntax, as Supabase projects already supply the `public` schema within their provided PostgreSQL database instance.
4. **ENUM Data Types:** Converted all MySQL `ENUM` types to `VARCHAR` with standard SQL `CHECK` constraints (e.g., `role VARCHAR(20) CHECK (role IN ('customer', 'admin'))`). This avoids the overhead of managing custom types while enforcing identical data integrity rules.
5. **On Update Trigger:** PostgreSQL does not natively support `ON UPDATE CURRENT_TIMESTAMP` in table definitions like MySQL. I implemented a generic PL/pgSQL function (`update_modified_column()`) and attached it via `BEFORE UPDATE` triggers on the `users` and `products` tables.
6. **Drop statements:** Converted `DROP TABLE IF EXISTS table_name` to `DROP TABLE IF EXISTS table_name CASCADE` to easily reset the database if needed, allowing referenced tables to drop cleanly.
7. **Sequence Adjustments (Sample Data):** Because sample data inserts specify explicit Primary Key IDs, the PostgreSQL identity sequence counters can fall behind. Included `setval(pg_get_serial_sequence(...))` statements after the insertions to manually sync the identity sequences with the maximum inserted ID, preventing conflict errors on subsequent row additions.

## 4. Issues & Assumptions
- **Constraint Naming:** Ensured that unique constraints (`UNIQUE (user_id, product_id)`) are explicitly named for easier schema migrations later on.
- **Identity Sequences:** Assumed `GENERATED BY DEFAULT` instead of `GENERATED ALWAYS` so that the provided sample data script containing explicit Primary Keys (e.g., `INSERT INTO users (user_id, ...`) can execute without error.
- **Boolean Type:** Supabase fully supports the `BOOLEAN` type. MySQL's `TINYINT(1)` boolean aliases have seamlessly translated to native PostgreSQL `BOOLEAN` without issue.
